# C3 人工审批 — 决策模板

## 1. 决策标识

| 字段 | 值 |
| --- | --- |
| decisionId | `C3` |
| 事项 | 无有效审批时 ready 返回「等待审批」；审批人须在项目指定名单、针对当前 HEAD、取最新审查状态，撤销/被要求修改覆盖的批准无效 |
| 形式 | 插件（审批判定）+ 项目配置（审批名单） |

## 2. 证据来源（甲提供）

- **假设**：对高风险交付增加人工把关，减少错误交付被放行。
- **合法用例**：名单内审批人批准当前 HEAD 后放行；等待审批时 Worker 停止并报告，审批后由宿主重新唤起（不永久 blocked）。
- **开发集误拦率**：合法交付被等待的比例；审批延迟对运行时长的影响。
- **副作用观察**：审批等待是否被错误计入失败重试上限（C4.5）；「插件+人工」合计效果如何与插件自身效果分离。
- **归因要求（关键）**：赫菲组加了人工审批而对照组没有时，收益是「插件加人工」的合计效果；启用审批的运行必须单独成组或单独分析，不能计入插件自身效果。
- **证据缺口**：以上全部待甲提供；当前无审批名单、无宿主唤起验证、无等待时长数据。

## 3. 选项

| 选项 | 说明 | 风险/成本 |
| --- | --- | --- |
| A. 维持关闭（默认） | 不启用审批 | 无新增风险；高风险交付缺少人工把关 |
| B. 全量启用（指定名单） | 所有 ready 均需有效审批 | 等待成本高；组别归因复杂 |
| C. 仅特定类别/高风险启用 | 如跨模块、缺陷修复等类别 | 需定义类别；分层分析 |
| D. 先只记录不拦截 | 记录「本应等待审批」的事件 | 不阻塞；但不等同于验证 |

## 4. 影响

- 对 B 线指标：引入人工介入成本；若组别不平衡会污染 D2/D4 的归因。
- 对样本量/成本/可比性：审批等待计入 wallClock 成本，必须与无审批组的分层可比；样本量可能增加。
- 开发者摩擦：等待审批；名单维护。
- 失败语义：无有效审批 ≠ 失败；不得计入失败重试上限，不得写 blocked 终态（按宿主机制报告等待）。
- 回滚：审批开关可关闭；回滚后既有记录保留并标注组别。

## 6. 默认（未批准时）

- 保持关闭：不启用审批判定、不配置审批名单；
- 不得把「等待审批」写成失败或在报告中计入失败重试；
- 若上游要求启用，先补本节证据并取得负责人书面批准。
